# 04 — NTLM Relay

## Objective

Relay a captured NTLM authentication from WINTERFALL to SMB services that were identified as not requiring SMB signing.

## Relay Targets

The relay targets were generated during the SMB signing enumeration stage:

| Host | IP Address | SMB Signing |
|---|---|---|
| CASTELBLACK | `192.168.56.22` | Disabled |
| BRAAVOS | `192.168.56.23` | Disabled |

The target list was stored in `relay-targets.txt` within the private evidence directory.

## ntlmrelayx

Impacket `ntlmrelayx` was used to receive and relay the NTLM authentication.

The system installation did not expose `ntlmrelayx` directly in the shell PATH, so the packaged example script was executed explicitly:

```bash
sudo python3 /usr/share/doc/python3-impacket/examples/ntlmrelayx.py \
  -tf relay-targets.txt \
  -smb2support \
  -socks
```

### Command breakdown

- `sudo` — provides the privileges required for the network listeners.
- `python3` — executes the installed Impacket Python script.
- `/usr/share/doc/python3-impacket/examples/ntlmrelayx.py` — the installed `ntlmrelayx` implementation used in this lab.
- `-tf relay-targets.txt` — supplies the file containing the SMB relay targets.
- `-smb2support` — enables SMB2 support for incoming and relayed SMB authentication.
- `-socks` — enables the SOCKS proxy functionality so successfully relayed connections can be registered as SOCKS sessions.

## Successful Relay

The authentication generated by `NORTH\robb.stark` from WINTERFALL was successfully relayed.

The relay process reported successful SMB authentication against both unsigned targets:

| Source Account | Source Host | Relay Target | Result |
|---|---|---|---|
| `NORTH\robb.stark` | WINTERFALL (`192.168.56.11`) | CASTELBLACK (`192.168.56.22`) | Successful SMB authentication |
| `NORTH\robb.stark` | WINTERFALL (`192.168.56.11`) | BRAAVOS (`192.168.56.23`) | Successful SMB authentication |

`ntlmrelayx` also registered SOCKS sessions for both successful relay connections.

## What Was Demonstrated

The exercise demonstrated that an NTLM authentication originating from one host could be successfully forwarded to other SMB services when those services did not enforce SMB signing.

This establishes a complete NTLM relay path within the GOAD environment:

```text
LLMNR/mDNS poisoning
        ↓
NTLMv2 authentication
        ↓
NTLM relay
        ↓
CASTELBLACK / BRAAVOS SMB authentication
```

## Scope Limitations

Successful relay authentication should not be interpreted as proof of administrative privileges or full system compromise.

The following were not demonstrated in this Part:

- Administrator access
- Domain Administrator access
- Privilege escalation
- Remote code execution
- Credential dumping
- Persistence

No post-relay exploitation was performed after the successful SMB authentication.
